# 体检规则

11 项检查。**9 项必做**（1/2/3/5/6/7/9/10/11），**2 项仅记录**（4/8）。

脚本（`scripts/scan.py`）能提供 1、5、6、7、9、10、11 的**候选项**；
2、3、4、8 必须由模型读 SKILL.md 后判断。**脚本给的是候选，不是结论。**

---

## 必做项

### 1. 失效引用

**判定**：某个 skill 的 SKILL.md 正文里引用了另一个 skill（`/name` 或裸 `name` 形式），
但该 skill 在 `~/.agents/skills/` 下不存在。

**候选来源**：`scan.json` 的 `unknown_slash_refs`（形如 `/grilling`）、
`unknown_name_refs`（形如 `` `grilling` `` 的反引号名式）与
`referenced_skills`（正文提到的已知 skill 名，用于确认引用方向）。

**两种引用写法都要查**：`/name` 形式与 `` `name` `` 反引号名式。
只查前者会漏掉用名式写下、但名字已不存在的断链。

**误报排除**（看到这些不要报）：
- 模板占位符（`<tmpdir>/architecture-review-<ts>.html` 里的片段）
- 目录名片段（`iteration-N`、`eval-0`）
- 文件名引用（`/SKILL.md`、`/scripts/scan.py`）
- 明确说了"不要用"的反向提及（`skill-creator` 里的 "Do NOT use `/skill-test`"）
- 普通路径、URL 片段

**唯一的例外排除规则（严格限定作用域）**：
`skills-management` 自己的文件（`skills-management/SKILL.md`、`references/checks.md`）
会把 `/grilling`、`/prototype` 这样的**名字当作举例**写在正文里（用于说明“断链长什么样”），
因此扫描会稳定地报出它们。
**这些是故意写的示例，不是真实断链**——真实断链指的是其他 skill 正文里指向不存在 skill 的引用。
**这条排除只对 `skills-management` 这一个 skill 生效**，不适用于任何其他 skill。

> 曾经出过的错：把这条排除规则套用到了 `decision-mapping` 和
> `improve-codebase-architecture` 上，于是把这两个文件里**真实存在的**断链
> 当成“自身举例”排除了，得出“断链 0 条”的错误结论。
> **判断依据是“这条引用出现在哪个文件里”，不是“这个名字看起来眼熟”。**
>
> 另一个坑：拿**已经修好的**旧例子当“当下仍然存在的候选举例”。
> 例子过期不会让闸门出错（闸门只管机械判定），但会让报告看起来像漏报了真问题。
> 写举例时用“历史上曾出现过的形态”这种说法，并标明它已修复。

**报告写法**：`正文调用 /X，该 skill 不存在` + 影响（"Prototype 型工单无法落地"）+ 建议动作。
**不要**擅自修改被检查的 skill 文件。

### 2. 命名不一致

**判定**：同一概念在不同文件里用了不同的名字。最常见的是
「`/grilling`（被引用名）」vs「`grill-me`（实际目录名）」。

**判定依据**：对比 `unknown_slash_refs` 里的名字与 `skills[].name`，
找出形近或语义等价的一对（`grilling`/`grill-me`、`domain-modelelling`/`ubiquitous-language`、
`domain-modelling`/`domain-modeling`）。

**报告写法**：`X 文件写作 /A，实际 skill 名为 B` + 影响 + 建议动作（统一到哪个、要不要保留别名）。
只报**能被证据支撑**的对，不确定就不报。

### 3. 功能重叠

**判定**：两个 skill 的 `description` 语义几乎相同，或正文描述的工作流程高度重合。

**判定依据**：读 `frontmatter.description` 全文对比。重叠要给出**具体证据**
（两段 description 的重合部分、相同的阶段划分），不能只说"感觉像"。

**报告写法**：`a 与 b 的 description 高度重合（都做 X、Y、Z）` + 差异点 + 建议动作
（保留哪个、另一个可删、或把两者明确分工）。

### 5. frontmatter 缺失 / description 过弱

**判定**（脚本已给出 `frontmatter.issues`）：
- 缺少 YAML frontmatter 整体
- 缺 `name` 或 `description`
- `description` < 40 字符（难以判断何时触发）或 > 1200 字符（触发判定噪音大）
- frontmatter `name` 与目录名不一致

**影响说明**：description 是 skill 被触发的**唯一机制**。
过弱的描述不是文档问题，是**功能性问题**——该 skill 可能永远不被选中。

### 6. SKILL.md 超长

**判定**：SKILL.md 超过 **500 行**。

**为什么是 500**：`skill-creator` 规定 SKILL.md 是"skill 一旦触发就全量进上下文"的一层，
500 行是它的预算上限。超长意味着每次触发都在烧 token。

**建议动作**：
- 把可按需加载的细节拆进 `references/`、`scripts/`、`assets/`
- 把**何时读哪个 reference** 的指引留在 SKILL.md 正文里
- 若主要是**原文引用**（如 skill-creator 引用了大量外部规范），可保留但要在正文标注"供参考，不必逐字读"

### 7. 硬编码路径

**判定**：SKILL.md 正文里写死了本机绝对路径（脚本 `hardcoded_paths` 字段）。

**典型例子**：`obsidian-vault` 里的 vault 路径 `/mnt/d/Obsidian Vault/AI Research/`。

**影响**：换机器 / 换 vault 即失效。

**建议动作**：改为"从环境变量读取，缺省为 `<默认值>`"或"首次运行时询问并记住"，
同时在文档里写清如何覆盖。

### 9. 引用写法不统一

**判定**：同一个 skill 集合里，引用其他 skill 的写法有两种——
`/name` 形式与 `` `name` `` 反引号名式。**约定用反引号名式**：
它是纯文本、可搜索、不会与路径混淆；`/name` 形式读起来像命令或路径。

**候选来源**：`scan.json` 的 `style_issues`（已知 skill 名却写成 `/xxx`）。

**报告写法**：`X 文件中 N 处写作 /name，应统一为 \`name\`` + 给一条 sed 命令。

### 10. 共享产物文件不一致

**判定**：两个 skill 把**同一个概念**写进**两个不同的规范文件**，导致一个写、一个读，
术语分叉。这类问题**不会以 `/name` 形式出现**，脚本按引用名根本抓不到。

**典型例子（已修复，作为模式记住）**：2026-10-20 之前，`ubiquitous-language` 写
`UBIQUITOUS_LANGUAGE.md`，而 `improve-codebase-architecture` 读写 `CONTEXT.md`——
两份词汇表，前者写的词后者读不到。现在两者统一为 `CONTEXT.md`。
**这类问题不会以 `/name` 形式出现**，按引用名根本抓不到。

**候选来源**：`scan.json` 的 `artifacts` 数组（每个规范产物的产出方 / 消费方），
以及 `gate` 的 `warnings`（词汇表类文件只被自己的产出方使用 → 自我闭环）。

**判定依据**：
- `orphan_consumer` = 被消费但集合内无人产出 → 一定是问题
- `self_only` = 词汇表类文件只被自己的产出方使用 → **线索**，需人工确认
  （也可能是"有意保留的旧名 + 迁移说明"）
- 两个不同的词汇表类文件同时存在，且各自自我闭环 → 高度可疑

**报告写法**：`A 写 X.md，B 读写 Y.md，同一概念两个文件` + 影响（"B 读不到 A 刚写的词"）
+ 建议动作（统一到哪个文件，附迁移说明）。

### 11. 编码损坏（U+FFFD）

**判定**：SKILL.md 正文里出现 **U+FFFD 替换字符**（Unicode 码点 U+FFFD，渲染为一个空心方块）。脚本 `mojibake` 字段。

**成因**：GBK / UTF-8 互转时丢字，或写入时被截断。肉眼看过去像正常中文，
但渲染出来是「口口口」，读者根本不知道原文是什么。

**为什么值得单列一项**：它不会让 skill 跑不起来，只是**静默地损坏语义**——
比断链更难发现。已实际抓到过：`skills-management/SKILL.md` 里
「覆盖本身不等**口口口**于静默」。

**报告写法**：`X 文件第 N 行有 M 个 U+FFFD 字符` + 给出正确文字 + 建议动作（替换掉）。

## 仅记录项（写下线索，但不下结论、不预填勾选框）

### 4. 孤儿 skill

**定义**：没有任何其他 skill 引用它，也不属于任何工作流。

**重要**：这**往往不是问题**。`teach`、`obsidian-vault`、`skill-creator` 这类
本身就是独立工具，不被别的 skill 调用完全正常。

**写法**：只写"未被其他 skill 引用"这一**事实**，不要写"应该删除"。

### 8. 疑似指令冲突

**定义**：同一个 skill 内部前后表述矛盾。

**难点**：很多看起来矛盾的话其实是**分场景**的。
例如 `teach` 里"知识难是敌人，技巧难是工具"不是冲突，是分别针对知识获取与技能习得。

**写法**：只有当**同一场景下**的说法确实互斥时才记录，并写出两处原文。
不确定就不写。

## 报告纪律

1. **只有两个文件可以写：`skills-description.md` 和 `skills-health.md`。**
   其他 skill 文件一律只读。写完用 `scan.py --compare` 核验（见 SKILL.md 第 5 步）。
   **"建议动作"是给人执行的命令，不是你的待办清单**——把它们原样交给人，
   不要自己动手。
2. **不删除 skill。** 功能重叠的取舍是使用习惯问题。
   需要删除时，在清单里给出**确切的命令**（如 `rm -rf ~/.agents/skills/<name>`），由人执行。
3. **区分"事实"与"线索"**。脚本输出的是事实（行数、路径、引用名）；
   重叠、冲突、孤儿是线索。措辞上不要把线索写成结论。
4. **每条问题都要有建议动作**。只列问题不给方向，等于把分析成本推回给人。
5. **"0 条"是需要证据的结论。** 写"断链 0 条""重叠 0 条"之前，
   必须能说出你**逐个核对过什么**。如果只是因为没在文件里看到，
   那叫"没查到"，不叫"不存在"。用词要准。
6. **闸门不是判官。** `scan.py --gate` 只收高置信度问题，用来回答
   "改完还有没有硬伤"。它通过**不代表**没有重叠、冲突、孤儿——
   那三项只有模型读过正文才能判断。
